Agent（智能体）

Agent — a system that pursues goals autonomously

生成工具：concept-study-materials Skill 生成日期：2026-09-04 核查状态：已人工核查 · 2026-09-04

PART 1学习目标

学完这份资料，你应该能够：

  1. 用自己的话说清 Agent 与普通 LLM 对话、与固定流程（workflow）的区别；
  2. 说出 Agent 的四个核心组成部分（大脑、规划、记忆、工具使用），并解释它们如何配合工作；
  3. 解释"循环"为什么是 Agent 的灵魂（感知 → 规划 → 行动 → 观察反馈）；
  4. 对一个具体任务判断"是否值得用 Agent 来做"，并说出理由。

PART 2核心问题

带着下面的问题往下读，读完回到这里检验自己能否回答：

同样是调用大模型，"AI 自主决定下一步做什么"和"开发者提前写好每一步"有什么本质区别？ Agent 在没有人逐步指挥的情况下，靠什么推进任务、又靠什么知道自己"做完了"？

PART 3我的解释

我理解的 Agent，是一个以大模型为"大脑"的软件系统：你交给它一个目标而不是一条条指令，它自己把目标拆解成步骤、挑选并调用工具、根据每一步的执行结果决定接下来做什么，循环往复直到目标完成。它和普通"AI 对话"最大的区别在于谁掌握流程——对话里流程在我手里，我一句句地问；Agent 里流程在它手里，它对一个目标负责到底。也正因为要自主决策，它比固定流程更灵活，但也更需要在关键动作上被监督。

PART 4核心机制与组成

学界常用"规划 + 记忆 + 工具使用"框架描述 Agent，它们都围绕 LLM 这个"大脑"运转：

组成部分它做什么对应的技术机制
大脑（LLM） 理解目标、推理、决定下一步行动 大语言模型的推理能力；通过上下文接收所有信息
规划（Planning） 把大目标拆成可执行的小步骤，并在出错时反思修正 思维链（CoT）；ReAct（推理与行动交替）；Reflexion（从失败反馈中学习）
记忆（Memory） 记住"现在正在做的任务"和"更早发生的事" 短期记忆 = 上下文窗口（对话与工具结果）；长期记忆 = 外部存储（文件、向量库、检索）
工具使用（Tool Use） 真正"动手"：搜索、执行代码、读写文件、调用 API 函数调用（Function Calling）、MCP 等工具协议

这些组件在一个工作循环里运转：

  1. 接收目标（如"完成这份作业并推送到 GitHub"）；
  2. 拆解规划（列出要做的事：建仓库 → 写 Skill → 生成资料 → 提交推送）；
  3. 调用工具行动（执行 git 命令、写文件）；
  4. 观察结果（命令成功了吗？报错信息是什么？网页能访问吗？）；
  5. 判断是否达成目标——没达成就带着新信息回到第 3 步，达成就交付并自检。

一个最小示例：让 Agent"把本周的学习笔记汇总成一页摘要并发到 GitHub"——它会先列出笔记文件、逐个读取、提炼要点、写摘要文件、执行 git 提交，遇到报错就读取错误信息、修正后重试，全程不需要人介入每一个步骤。

Anthropic 在工程实践中给出过一个重要区分：workflow 是开发者用代码预先编排好 LLM 的调用路径；Agent 则是 LLM 在循环中动态决定自己的过程。他们的工程建议是：从最简单的方案开始，确实需要时才增加自主性——能用单次调用解决的，不要用 workflow；能用 workflow 解决的，不要上 Agent。

PART 5具体应用场景

场景：用 WorkBuddy（一个 Agent）完成本次课程作业

这本身就是一次真实的 Agent 运行。我给出的只有作业要求（建仓库 → 做项目级 Skill → 生成三份学习资料 → 提交推送），没有给出任何一步具体命令。之后发生的一切都是它自主推进的：

  • 行动：先检查环境——git 是否安装、GitHub CLI 是否登录；
  • 观察：发现环境可用，于是创建远程仓库并克隆到本地；
  • 行动：加载 Skill 创建规范，初始化项目级 Skill 目录；
  • 观察与调整：核实资料来源时，某官方文档页面因区域限制无法访问，Agent 没有卡住，而是自动检索并替换为可访问的权威来源（IBM 官方科普页面）；
  • 循环推进：按流程生成资料 → 自检 → 请求我核查。

整个过程里"下一步做什么"都由它根据上一步的结果决定；我（人）只在最初设定目标、在中间做关键设计决策（仓库名、Skill 名）和最后核查结果。这正是 Agent 与工具的本质分工。

其他常见场景（简列）：AI 编程助手修复一个 bug（读代码 → 定位 → 修改 → 跑测试 → 再修改）；客服 Agent 查订单 → 改地址 → 发确认邮件。

PART 6概念辨析

易混淆对象关键区别一句话判据
Agent vs. LLM 对话 / Chatbot Chatbot 只生成文本回应；Agent 调用工具、改变外部世界的状态 它能不能"动手做事"，而不只是"说话"
Agent vs. Workflow Workflow 由开发者预先编排好每一步 LLM 怎么被调用；Agent 由模型在循环中动态决定流程 任务的步骤能不能被提前穷举写死
Agent vs. RPA / 固定脚本 RPA 按确定性规则执行，遇到没见过的情况就停；Agent 用自然语言推理应对意外 遇到预料外的情况会不会"想办法"
Agent vs. 机器人（硬件） AI 语境下的 Agent 通常指软件系统，不需要物理实体 有没有身体不是判据，自主性才是

PART 7使用边界

适合用的情形：步骤无法预先穷举的开放性任务；需要综合多来源信息并随中间结果调整策略的任务，如深度调研、资料整理、复杂代码修复、多步骤文件处理与办公自动化。

不适合 / 会失效的情形：

  • 步骤完全确定的流水线任务——用 workflow 或普通脚本更可控、成本更低；
  • 对准确性零容忍、且没有人工把关环节的决策——自主性会带来错误的累积与放大；
  • 单步就能解决的简单问题——直接一次调用即可，用 Agent 是浪费；
  • 需要跨会话长期记忆的任务——受上下文窗口限制，Agent 天生"健忘"，需外置记忆配合。

PART 8自测问题

共 10 题，按"基础 → 进阶 → 挑战"三级难度分层，覆盖解释、机制、场景、边界四个维度。先自己作答，再展开核对；答不上来就回到对应章节重读。

基础1. 按照本资料，Agent 与普通 LLM 对话（Chatbot）最本质的区别是？

  1. Agent 不需要提示词
  2. Agent 使用的模型参数量更大
  3. Agent 能调用工具、改变外部世界的状态，而 Chatbot 只生成文本回应
  4. Agent 只能运行在本地电脑上
答案与解析

答案：C。判据是"能不能动手做事"：Chatbot 只生成文本，Agent 通过工具调用改变外部世界。（PART 6 对比表）

基础2. Lilian Weng 的经典框架中，Agent 除"大脑（LLM）"外的三大核心组件是？

  1. 输入、处理、输出
  2. 规划（Planning）、记忆（Memory）、工具使用（Tool Use）
  3. 感知、决策、执行
  4. 编码、训练、部署
答案与解析

答案：B。规划负责拆解与反思，记忆分短期（上下文）与长期（外置存储），工具使用负责真正"动手"。（PART 4 组件表）

基础3. Agent 的"短期记忆"由什么技术承载？

  1. 模型权重
  2. 关系型数据库
  3. 显卡显存
  4. 上下文窗口
答案与解析

答案：D。短期记忆 = 上下文窗口，容量按 token 计；长期记忆才需要文件、向量库等外部存储。（PART 4）

进阶4. 区分 workflow 与 Agent，最可靠的判断依据是？

  1. 任务流程由开发者预先编排（workflow），还是由模型在循环中动态决定（Agent）
  2. 二者只是叫法不同，没有实质区别
  3. 调用了外部 API 的就是 Agent
  4. Agent 一定联网，workflow 不联网
答案与解析

答案：A。核心是"谁掌握流程"：workflow 的调用路径写在代码里，Agent 的路径由模型边执行边决定。（PART 4、PART 6）

进阶5. 在"行动 → 观察 → 调整"的循环中，"观察"环节的作用是？

  1. 压缩过长的对话历史
  2. 让用户实时观看执行过程
  3. 把执行结果（输出、报错、新信息）写回上下文，作为下一步决策的依据
  4. 暂停任务，等待人工确认
答案与解析

答案：C。观察 = 感知行动结果并送回"大脑"。没有这一步，Agent 就无法根据反馈调整策略。本作业中"遇到区域受限链接自动换来源"正是观察环节在起作用。（PART 4 循环、PART 5）

进阶6. ReAct、Reflexion 这类技术主要增强 Agent 的哪方面能力？

  1. 上下文窗口容量
  2. 规划与从失败反馈中反思修正的能力
  3. 工具调用的网络速度
  4. GPU 算力利用率
答案与解析

答案：B。ReAct 让推理与行动交替进行，Reflexion 让模型从失败结果中总结经验修正策略——两者都属于"规划"组件的机制。（PART 4）

进阶7. 场景判断："每周一凌晨自动从固定数据库导出固定格式的报表并发送邮件"，更合适的方案是？

  1. workflow 或普通定时脚本——步骤完全确定，无需模型自主决策
  2. 只能人工完成
  3. 用 Agent，因为它更省钱
  4. 必须用 Agent，否则无法完成
答案与解析

答案：A。任务步骤可以提前穷举，按"最简单方案优先"原则，确定性流程用 workflow/脚本更可控、成本更低。（PART 7 使用边界）

挑战8. "没有工具使用就没有真正的 Agent"，最准确的理由是？

  1. 工具是硬件，Agent 必须依赖硬件运行
  2. 工具能提高模型的智力水平
  3. 工具能扩大上下文窗口
  4. 不调用工具就无法改变外部状态、获取实时信息，任务闭环无法形成
答案与解析

答案：D。只生成文本的模型"动嘴不动手"，无法把任务推进到真实世界的变化；工具是 Agent 的"手脚"，与智力无关。（PART 4、PART 8 Q3 联动）

挑战9. Anthropic 建议"从最简单的方案开始，需要时才增加自主性"，背后的工程逻辑是？

  1. 简单方案完全不需要维护
  2. 自主性在带来灵活性的同时，也带来错误累积、成本上升与不可控风险
  3. 复杂框架在技术上无法实现
  4. Agent 的性能瓶颈是硬件问题，与方案复杂度无关
答案与解析

答案：B。每一步自主决策都有出错和放大的可能，且 Agent 循环越多轮越贵——只有在步骤无法穷举时才值得付出这个代价。（PART 4、PART 7）

挑战10. 一个 Agent 在执行中途遇到从未预料的报错，自行调整策略后完成任务。对这种能力来源的解释，最准确的是？

  1. 开发者预先写死了所有可能的错误分支
  2. 训练数据中包含了这道报错的标准答案
  3. 模型基于上下文中的报错信息进行推理，动态决定新的步骤
  4. 系统随机尝试，碰巧撞对了方案
答案与解析

答案：C。应对"没见过的情况"靠的是推理而非穷举——这是 Agent 区别于 RPA/固定脚本的本质（PART 6）。B 有迷惑性：训练给的是一般化能力，不是这道具体报错的答案。
