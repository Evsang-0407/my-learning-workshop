大模型的上下文

Context & Context Window — the working memory of an LLM

生成工具：concept-study-materials Skill 生成日期：2026-09-04 核查状态：已人工核查 · 2026-09-04

PART 1学习目标

学完这份资料，你应该能够：

  1. 解释上下文窗口是什么、以什么单位衡量、里面装了哪些东西；
  2. 说明上下文的底层处理机制（token 化 + 自注意力）；
  3. 描述上下文如何制约 Agent 的工作方式（有限容量、"迷失在中间"效应、成本）；
  4. 说出至少三种应对上下文有限的常见工程策略。

PART 2核心问题

带着下面的问题往下读，读完回到这里检验自己能否回答：

为什么大模型会"聊着聊着就忘了前面说过的话"？把上下文窗口从 4K 扩到 1M，是不是所有问题就迎刃而解了——还是带来了新的问题？

PART 3我的解释

我理解的"上下文"，是模型在一次推理中能"看见"的全部输入——系统提示、我们说过的话、工具返回的结果、贴进去的文档，全都装在一个叫上下文窗口的容器里。它就像模型的"工作记忆"：容量按 token 计算，装不下的就会被截断或压缩掉。这个容器有几个关键事实：它不只是装"我说的话"；它越大算得越贵、越慢；而且装得下不等于用得好——模型对开头和结尾的信息利用得最好，长文本中间的内容容易被"忽略"。对 Agent 来说，上下文就是它唯一的工作现场：它的一切决策，都取决于此刻窗口里有什么。

PART 4核心机制与组成

1）token 化：上下文的计量单位。模型处理语言的最小单位不是字，而是 token——可能是一个字、半个词或一小段常用短语。IBM 的科普给出一个实用估算：英文约 1.5 个 token 对应一个词；而不同语言的 token 效率差异很大（同样的句子，某些语言消耗的 token 可能是英文的好几倍），中文也普遍比英文"贵"。这也是为什么"能装多少字"没有统一答案。

2）自注意力：上下文的处理机制。Transformer 架构用自注意力（self-attention）计算序列中每个 token 与其他 token 的相关性权重，逐 token 生成输出时不断"回看"前文。这个机制是一切的基础（"Attention Is All You Need"，2017），也是限制的来源：注意力计算量随序列长度平方级增长——token 数翻倍，计算量约变 4 倍，推理更慢、更贵。

3）上下文窗口里装的不止是你的话：

内容说明
系统提示（System Prompt）常被隐藏、用户看不见，规定模型的行为方式
对话历史你说过的每句话和模型的每次回复
工具返回结果Agent 场景下，搜索结果、命令输出、文件内容都占这里的空间
检索注入的资料RAG 从外部知识库检索来的文档片段
格式字符换行、特殊符号等格式开销也消耗 token

4）"迷失在中间"（Lost in the Middle）：斯坦福等机构 2023 年的研究发现，模型利用长上下文的能力并不均匀——相关信息位于开头或结尾时表现最好，位于中间时性能显著下降，即使是长上下文模型也是如此。这说明：窗口大 ≠ 中间的内容被好好用了。

5）窗口大小的量级（变化很快，仅作参照）：按 IBM 文章截至 2024-10 的数据：GPT-3.5 为 4K~8K，GPT-4/4o 与 Llama 3.1 为 128K，Claude 3.5 Sonnet 约 200K，Gemini 1.5 Pro 最高达 2M token。三年间扩大了数百倍，且仍在增长。

6）常见的应对策略：超长内容先检索后注入（RAG）、对话历史摘要压缩、把稳定知识外置成文件按需读取（而非全程占据窗口）、以及把可复用流程沉淀成 Skill 按需加载。

PART 5具体应用场景

场景：用 AI 编程助手（Agent）处理一个大型项目

假设一个有几十万行代码的仓库要交给 AI 助手维护。第一种做法是把整个代码库塞进上下文——很快会发现：一是塞不下（超过窗口上限），二是塞得下也太贵太慢（注意力计算平方级增长），三是即使塞进去了，目标代码"迷失在中间"，模型照样出错。

实际工程中的做法是分层"喂"：

  • 常驻上下文的只有精炼的项目说明（约定、结构、注意事项）；
  • 需要某段代码时，用搜索工具定位并只读取相关文件；
  • 执行命令的输出只在需要时查看，不相关的输出不进入后续对话；
  • 可复用的操作规范沉淀成 Skill，触发时才加载进来。

我在完成本次作业时就亲历了这个逻辑：生成资料需要核实 9 个来源，但助手并没有把所有网页全文都装进上下文，而是按需抓取、即时消化、只保留结论——这就是在上下文稀缺的约束下工作的真实样子。

其他常见场景（简列）：长文档问答（超长 PDF 分段检索后再注入）；多轮长对话自动摘要早期内容，防止"遗忘"关键约定。

PART 6概念辨析

易混淆对象关键区别一句话判据
上下文窗口 vs. 训练数据 窗口是推理时"此刻可见"的工作记忆；训练数据是训练时沉淀进模型权重的长期知识 窗口里的它会"看见"，训练数据里的它只"记得大概"
上下文窗口 vs. 长期记忆（Memory） 窗口是模型内置且有限的；长期记忆靠外部存储（文件、向量库），需要工程手段挂接 关掉会话还在不在
上下文学习（in-context learning）vs. 微调（fine-tuning） 前者把示例放进上下文，改的是"这次输入"；后者改的是模型权重，成本和效果都完全不同 改提示词 or 改模型本身
token vs. 字 / 词 token 是模型视角的最小单位，与人类语言的字词不是一回事，且不同语言效率不同 谈窗口容量时必须用 token 计量

PART 7使用边界

适合依赖大上下文的情形：长文档整体理解（跨段落的综合与对照）；长对话中保持连贯；一次性给出充足的领域资料让模型"现场学会"（上下文学习）。

不适合 / 需要警惕的情形：

  • 以为"窗口大就往里塞一切"——中间信息利用率下降（Lost in the Middle），且成本随长度平方级增长；
  • 把敏感信息（密码、隐私、密钥）放进上下文——既可能被记录，也可能被注入的恶意指令读取，IBM 的文章还指出更长的上下文会带来更大的对抗攻击面；
  • 指望窗口替代长期记忆——会话一结束，窗口里的内容就没了，需要沉淀的东西应外置保存；
  • 引用具体模型参数（如"128K 窗口"）时必须注明版本与时间点——这个数字变化极快。

PART 8自测问题

共 10 题，按"基础 → 进阶 → 挑战"三级难度分层，覆盖解释、机制、场景、边界四个维度。先自己作答，再展开核对；答不上来就回到对应章节重读。

基础1. 上下文窗口的容量以什么为单位衡量？

  1. 字数
  2. token
  3. 字节
  4. 页数
答案与解析

答案：B。模型处理语言的最小单位是 token，可能是半个词、一个字或一小段短语；谈窗口容量必须用 token 计量。（PART 4）

基础2. 下列哪一项通常不占用上下文窗口的空间？

  1. 工具返回的结果
  2. 系统提示（System Prompt）
  3. 对话历史
  4. 模型的训练数据
答案与解析

答案：D。训练数据在训练时已沉淀进模型权重，属于"长期知识"，不占推理时的窗口；其余三项都在窗口里。（PART 4 窗口内容表、PART 6 辨析）

基础3. 资料把"上下文"类比为模型的什么？

  1. 工作记忆
  2. 长期知识库
  3. 性格
  4. 硬盘
答案与解析

答案：A。上下文是推理时"此刻可见"的工作记忆；训练数据才是长期知识，关掉会话还在的得靠外部存储。（PART 3、PART 6）

进阶4. 基于自注意力机制，注意力计算量随序列长度如何增长？

  1. 线性增长
  2. 对数增长
  3. 平方级增长
  4. 与长度无关
答案与解析

答案：C。token 数翻倍，计算量约变 4 倍——这是长上下文"更慢更贵"的直接原因。（PART 4）

进阶5. "Lost in the Middle"研究的核心发现是？

  1. 模型完全无法处理超过 1 万 token 的文本
  2. 相关信息位于开头或结尾时表现最好，位于中间时性能显著下降
  3. 模型只能记住对话的最后一句
  4. 窗口越大，中间位置信息利用率越高
答案与解析

答案：B。位置效应：即使是对长上下文优化的模型也如此；这解释了"窗口大 ≠ 用得好"。（PART 4、PART 7）

进阶6. 长对话中模型"聊着聊着就忘了前面说过的话"，最准确的原因是？

  1. 模型被设计成故意遗忘旧信息
  2. 网络连接不稳定导致消息丢失
  3. 累计内容超过窗口容量，早期内容被截断或摘要压缩
  4. 对话过程中模型权重被更新了
答案与解析

答案：C。对话历史全部装在有限的窗口里，超了就要截断/压缩，表现为"遗忘"。（PART 3、PART 4）

进阶7. 自注意力机制在上下文处理中的基本作用是？

  1. 计算序列中每个 token 与其他 token 的相关性权重
  2. 对输入文本进行加密传输
  3. 把文字切分成 token（分词）
  4. 压缩模型体积，降低显存占用
答案与解析

答案：A。逐 token 生成时不断"回看"前文并计算相关性，这是模型利用上下文（也是成本平方级增长）的根源。（PART 4；分词是另一回事）

挑战8. RAG（检索增强生成）能缓解上下文压力的原理是？

  1. 它降低了 token 化的字符开销
  2. 它扩大了模型的上下文窗口上限
  3. 它修改了模型权重，让模型记住更多
  4. 它只把检索到的相关片段注入上下文，而非把全部资料塞入
答案与解析

答案：D。RAG 改变的是"进窗口的内容"而不是"窗口本身"——先检索后注入，是应对窗口稀缺的按需策略。（PART 4 应对策略、PART 5）

挑战9. 关于"把窗口从 4K 扩到 1M"，下列说法最准确的是？

  1. 长上下文模型不受"迷失在中间"效应影响
  2. 容量问题解决后，中间信息的利用率问题也随之解决
  3. 窗口扩大在缓解容量的同时，带来成本、中间利用率下降与攻击面增大等新问题
  4. 窗口大小与推理成本无关
答案与解析

答案：C。更大窗口 = 更贵更慢（平方级）+ 中间信息利用率下降 + 更大的对抗攻击面；研究明确指出长上下文模型同样受位置效应影响。（PART 4、PART 7）

挑战10. "把示例直接放进提示词让模型现学"（上下文学习）与"微调"的对比，正确的是？

  1. 两者都改变了模型权重
  2. 前者改变的是这一次的输入（上下文），后者改变的是模型权重
  3. 两者效果与成本完全等价
  4. 微调不需要训练数据和算力
答案与解析

答案：B。上下文学习改"这次输入"，即写即用、会话结束即失效；微调改模型本身，需要数据和算力，但效果持久。（PART 6 辨析表）
