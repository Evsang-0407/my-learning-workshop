Skill（AI 智能体的技能）

Skill — packaged procedural knowledge an agent loads on demand

PART 1学习目标

学完这份资料，你应该能够：

  1. 说清 Skill 是什么、解决什么问题（把重复的任务知识沉淀成可复用能力）；
  2. 描述 SKILL.md 的结构（YAML 元数据 + 指令正文）与渐进式披露机制；
  3. 区分用户级与项目级 Skill 的存放位置和作用范围；
  4. 对一个重复出现的任务，判断"是否值得做成 Skill"，并知道动手做的最小路径。

PART 2核心问题

带着下面的问题往下读，读完回到这里检验自己能否回答：

同样的任务说明，为什么要反复粘贴进对话，而不能"教一次、永远会"？Skill 的内容什么时候才会进入模型的上下文，为什么要这样设计？

PART 3我的解释

我理解的 Skill，是把"某类任务该怎么做"的程序性知识打包成模型可以按需加载的文件夹：一个 SKILL.md 说清适用场景、步骤和输出要求，还可以带上脚本、参考资料和模板。它解决的是"重复教学"问题——与其每次都在对话里重新描述一遍怎么做事，不如写一次、之后自动生效。Anthropic 的工程师把它类比成给新员工写的入职手册，我很认同这个类比：它不改变员工（模型）的智力，只改变他的"熟悉程度"。最妙的是加载方式：平时只有一张"目录卡片"（名称 + 描述）摆在模型的案头，真正干活时才把手册正文翻开——既不浪费上下文，又随时可用。

PART 4核心机制与组成

1）基本结构：一个 Skill 就是包含 SKILL.md 的目录：

组成必需性作用
SKILL.md — YAML 元数据必需文件顶部 --- 之间的 name 和 description，是模型的"目录卡片"，决定它判断这个 Skill 何时相关
SKILL.md — 指令正文必需适用场景、输入、步骤、输出结构、自检要求等操作指南
scripts/可选可执行脚本，需要确定性可靠时用，执行不必载入上下文
references/可选详细参考资料，需要时才读入
assets/可选模板、字体等产出时使用的资源

2）渐进式披露（Progressive Disclosure）——Skill 最核心的机制：

  1. 第一级：会话开始时，只有每个 Skill 的 name + description 进入系统提示（约百字级）；
  2. 第二级：模型判断某 Skill 与当前任务相关时，才读取完整 SKILL.md 正文；
  3. 第三级：SKILL.md 里指向的脚本、参考资料，在真正需要时才加载或直接执行。

这个三层设计是对"上下文稀缺"的直接回应：不相关的知识不占窗口，相关的知识按需展开。

3）存放位置决定作用域：

级别位置作用范围
用户级~/.workbuddy/skills/（对应 Claude Code 的 ~/.claude/skills/）跟随个人账号，跨所有项目可用
项目级仓库内 .workbuddy/skills/（对应 .claude/skills/）随仓库共享，所有打开该仓库的人可用

本仓库的 .workbuddy/skills/concept-study-materials/ 就是一个项目级 Skill 的实例。

4）开放标准：Agent Skills 已于 2025 年 12 月作为开放标准发布（agentskills.io），同一套 Skill 结构可以在多种 AI 工具间通用——这也是把作业 Skill 放进仓库、而不是只存在某次对话里的意义：它是可迁移、可迭代的资产。

PART 5具体应用场景

场景：用本仓库的 concept-study-materials 学一个新概念（如"假设检验"）

这是我个人设计并实际用过的例子。设想下周统计课要学"假设检验"，我在 WorkBuddy 中打开本仓库，直接说："帮我学习假设检验"。

  • 会话启动时，模型案头已经有这个 Skill 的"目录卡片"（name + description），它判断"学习概念"的请求与它匹配；
  • Skill 正文被加载：界定概念 → 联网检索并逐条核实来源 → 按九部分结构撰写 → 套用 assets 里的 HTML 模板 → 自检 → 邀请我核查；
  • 产出 learning-materials/hypothesis-testing.html——包含学习目标、我的解释、机制、场景、辨析、边界、自测题和可核查来源；
  • 整个过程我不再重复解释"资料要长什么样、来源要怎么核"，因为这些都沉淀在 Skill 里了。

对比没有 Skill 时：每次都要把九部分要求、来源规范、自检清单重新粘贴一遍，还容易漏项。这就是"教一次、永远会"。

其他常见场景（简列）：企业把内部规范做成项目级 Skill，全组共享统一的报告格式；个人把"周报怎么写"做成用户级 Skill，在任何项目中调用。

PART 6概念辨析

易混淆对象关键区别一句话判据
Skill vs. 提示词模板 模板是被动的文本替换；Skill 可被模型按元数据自主发现、分级加载、还可捆绑脚本与资源 模型能不能"自己发现并按需打开"它
Skill vs. 微调 / 训练 Skill 改的是推理时进入上下文的知识，不动模型权重；微调改的是权重，需要数据和算力 改提示 or 改模型本身
Skill vs. 常驻系统提示 常驻内容永远占据上下文；Skill 通过渐进式披露，需要时才占用 不使用时是否消耗上下文
Skill vs. MCP / 连接器 MCP 给模型接入新的数据源和操作能力（"新手"）；Skill 教模型怎么把事做好（"方法"） 提供新工具 or 沉淀做事流程

PART 7使用边界

适合做成 Skill 的情形：重复出现的多步骤流程（如"生成学习资料""写周报"）；个人或团队的固定约定（文档格式、检查清单）；需要稳定可复用的领域操作规范。

不适合 / 需要警惕的情形：

  • 一次性任务——直接在对话里说清楚即可，做 Skill 是过度工程；
  • 敏感信息不要写进项目级 Skill——它会随仓库公开（本作业的 .gitignore 就为此排除了密钥类文件）；
  • 频繁变化的纯事实数据（如每日行情）——放外部数据源按需查询更好，Skill 适合沉淀"稳定的流程"；
  • description 写得含糊，模型就无法正确判断何时触发——元数据质量决定 Skill 的可用性。

PART 8自测问题

先自己作答，再展开核对。答不上来就回到对应章节重读。

Q1：Skill 解决的核心问题是什么？

把"怎么做某类任务"的程序性知识从一次性对话中沉淀出来，变成可发现、可复用、可共享的能力单元——"教一次、永远会"。（PART 3）

Q2：渐进式披露分几级？为什么说它是对上下文稀缺的回应？

三级：name+description 常驻 → 相关时加载 SKILL.md 正文 → 捆绑资源按需加载/执行。不相关的知识不占上下文窗口，相关的按需展开，节省稀缺的窗口空间。（PART 4）

Q3：项目级 Skill 和用户级 Skill 分别放在哪？作用范围有何不同？

用户级在 ~/.workbuddy/skills/（跨所有项目跟随个人）；项目级在仓库 .workbuddy/skills/（随仓库共享给所有打开它的人）。（PART 4）

Q4：SKILL.md 的 YAML 元数据里哪一项决定了模型能否正确触发它？

description——模型根据描述判断当前任务是否与该 Skill 相关；写得含糊就会漏触发或误触发。（PART 4、PART 7）

Q5：什么样的任务不值得做成 Skill？

一次性任务（直接对话即可）、包含敏感信息的内容（会随仓库公开）、频繁变化的纯事实数据（应外置为数据源）。（PART 7）
