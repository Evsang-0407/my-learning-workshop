01三个概念的一句话定位

概念一句话定位它回答的问题
Agent以 LLM 为大脑、在循环中自主调用工具完成目标的系统谁来执行、怎么推进任务
大模型的上下文模型单次推理能"看见"的全部输入，容量按 token 计的"工作记忆"执行时模型能依据什么
Skill把可复用的任务知识打包成模型可按需加载的文件（SKILL.md + 资源）经验如何沉淀、复用与共享

我的总理解是：Agent 负责"执行"，上下文是执行的"现场"，Skill 让执行"越做越好、越做越专"。三者不是并列的三个功能，而是一个系统里的三种角色。

03上下文如何影响 Agent 的工作

上下文是 Agent 唯一的"工作现场"：它感知的目标、记住的历史、工具返回的反馈，全部要经由上下文进入模型。因此上下文的三个特性直接塑造了 Agent 的工作方式：

  1. 有限性 → Agent 必须管理注意力。窗口装不下所有信息，所以真实 Agent 系统都用"按需读取"策略：搜索定位、只读相关文件、无关输出不进窗口（我在完成本作业核实来源时，助手就是按需抓取网页而非全文塞入）。
  2. 位置效应 → 重要信息要放对地方。"迷失在中间"研究表明模型对开头结尾的信息利用最好，所以给 Agent 的关键指令通常放在系统提示（最前），而不是埋在长文档中段。
  3. 成本随长度增长 → Agent 的"思考"是有价的。注意力计算量随长度平方级增长，Agent 循环越多轮、历史越长，每一步都更贵更慢，这决定了 Agent 的任务拆解不能无限细。

换句话说：上下文的稀缺性，是 Agent 工程化设计的第一约束。

04Skill 如何沉淀可复用的任务知识

如果说上下文的特性带来了约束，Skill 就是为化解这种约束而生的工程答案之一：

  1. 沉淀：从"易失"到"持久"。一段有效的做法如果只存在于对话历史里，会话结束就消失了；写成 SKILL.md 落在磁盘上，就变成了可版本管理、可迭代的资产（本仓库本身就在演示这一点）。
  2. 复用：渐进式披露对冲上下文稀缺。Skill 平时只有 name + description 占据极小的上下文空间，被判断相关时才加载正文，捆绑资源更晚加载——"知识待在磁盘上，需要时才进入现场"。
  3. 共享：项目级 Skill 让知识随仓库流动。放在仓库 .workbuddy/skills/ 里的 Skill，对每一个打开这个仓库的人生效，团队约定因此可以像代码一样被 review、被提交。

同时，Skill 也反过来改变 Agent 的能力边界：通用 Agent 谁都能用但不专精；加载了某个 Skill 的 Agent 立刻获得该领域的流程、规范和工具知识——就像新员工拿到了入职手册。

05一个闭环实例：本次作业如何同时用到三者

生成这三份学习资料的过程，恰好是三个概念的一次完整协作：

  1. 我（人）在 WorkBuddy 里发出目标：完成作业（此时，一个 Agent 开始运转）；
  2. 它按需加载了 Skill 创建规范和本仓库的 Skill（concept-study-materials 的说明进入它的上下文）；
  3. 在循环中：检查环境 → 建仓库 → 核实来源（遇到区域受限链接，依据反馈换来源）→ 生成资料 → 自检——每一步的决策都由当时的上下文决定，每一步的执行结果又写回上下文；
  4. 最后，"九部分结构 + 来源核实 + 自检清单"这套被验证有效的流程，以 SKILL.md 的形式沉淀下来——下一个概念（比如"假设检验"）可以直接复用。

我的个人判断：这三个概念里最容易被低估的是上下文管理。大家追逐 Agent 的自主性、比拼 Skill 的数量，但日常体验的好坏往往取决于"此刻窗口里放了什么"。同样地，Agent 的能力上限并不等于模型智力，而在于三者的工程组合——这也是为什么"从最简单的方案开始"（Anthropic 的工程建议）比"堆砌复杂框架"更接近用好 AI 的正确路径。

06综合自测（10 道选择题）

本页题目不考单个概念的背诵，而考三个概念之间的关系：上下文如何约束 Agent、Skill 如何化解这种约束、以及三者如何构成一个闭环。难度按"基础 → 进阶 → 挑战"分三层（3 / 4 / 3）。先自己作答，再展开核对。

基础1. 下列三组"概念 → 定位"的对应，全部正确的是？

  1. Agent = 聊天界面；上下文 = 联网功能；Skill = 快捷指令
  2. Agent = 模型参数；上下文 = 训练数据；Skill = 数据集
  3. Agent = 自主执行的大脑；上下文 = 运行时的工作现场；Skill = 沉淀下来的可复用任务知识
  4. Agent = 提示词；上下文 = 输出长度；Skill = 插件商店
答案与解析

答案：C。三者不是并列的三个功能，而是同一系统里的三种角色：Agent 负责执行，上下文是执行的现场，Skill 让执行越做越专。（章节 01）

基础2. 一个 Skill 尚未被触发时，它占据上下文的是哪一部分？

  1. 只有 name 与 description 这两行元数据
  2. 完全不占任何上下文，也完全不为人知
  3. SKILL.md 全文
  4. 它捆绑的所有脚本与资源文件
答案与解析

答案：A。这就是"渐进式披露"：平时只花极小上下文让模型知道"有这个技能及其适用场景"，判断相关后才加载正文，资源更晚才读。B 错在"完全不为人知"——没有那两行元数据，模型根本无从判断该不该用它。（章节 04）

基础3. 上下文窗口的容量用什么计量？

  1. 字节数
  2. 句子数
  3. 字符数
  4. token 数（模型处理文本的基本单位）
答案与解析

答案：D。上下文是"模型单次推理能看见的全部输入"，容量按 token 计；这也是为什么它被称为模型有限的"工作记忆"。（章节 01）

进阶4. 真实 Agent 系统普遍采用"按需读取"（搜索定位、只读相关文件）而非把资料全塞进上下文，主要原因是？

  1. 读取文件的 API 比网络请求便宜
  2. 窗口容量有限，且注意力计算成本随长度增长，无关信息还会稀释有效信号
  3. 模型无法一次处理多个文件
  4. 这样做可以让模型跳过推理直接输出
答案与解析

答案：B。有限性与成本是硬约束：窗口装不下所有信息，塞得越满越贵越慢，中间还容易"迷失"。本作业核实来源时按需抓取网页而非全文塞入，正是这一策略。（章节 03）

进阶5. "迷失在中间（Lost in the Middle）"这一发现，对 Agent 的工程实践最直接的可操作启示是？

  1. 只要上下文足够长，位置效应就会自动消失
  2. 尽量缩短用户的问题长度
  3. 把关键指令放在上下文的开头或结尾，而不是埋在长文档中段
  4. 把所有信息都改写成表格
答案与解析

答案：C。模型对开头与结尾的信息利用最好，所以关键约束通常放在系统提示（最前）。A 是常见误解：加长窗口并不能消除位置效应。（章节 03）

进阶6. Skill 与"一段写得很好的一次性提示词"相比，最本质的区别是？

  1. Skill 使用了特殊语法
  2. Skill 被持久化成磁盘上的文件资产，可版本管理、可迭代、可跨会话复用
  3. Skill 只能由官方发布
  4. Skill 更长
答案与解析

答案：B。只存在于对话历史里的做法，会话结束就消失；写成 SKILL.md 落在磁盘上，就变成能被 git 管理、能被 review、能持续迭代的资产——本仓库本身就在演示这一点。（章节 04）

进阶7. 把 Skill 放在仓库的 .workbuddy/skills/ 目录（项目级）而非个人全局目录，其意义在于？

  1. 项目级 Skill 的执行速度更快
  2. 放在这里可以避免占用上下文
  3. 只有项目级目录能被 Git 追踪
  4. 知识随仓库流动——每个打开该仓库的人都会自动获得这套约定，且可像代码一样被评审
答案与解析

答案：D。项目级 Skill 让团队约定从"口头传递"变成"随仓库分发"。C 错在因果关系——能否被追踪取决于是否提交进仓库，与目录层级无关。（章节 04）

挑战8. 一个 Agent 已经加载了高质量的 Skill，但某次任务依然表现糟糕。从三者关系看，最可能的原因是？

  1. Skill 决定"能力的上限"，而此刻上下文里装了什么才决定"这次的实际表现"——关键输入没进窗口，能力就无从发挥
  2. 模型参数量不足
  3. Skill 与 Agent 不兼容，必须更换模型
  4. 该 Skill 本身写得不好
答案与解析

答案：A。这是我想强调的核心判断：Skill 是可持久化的能力，上下文是能力得以兑现的现场。D 是干扰项——若 Skill 已被验证有效，则应优先排查"此刻窗口里放了什么"，而不是急着改 Skill。（章节 03、04）

挑战9. 关于三者关系，下列判断最准确的是？

  1. Agent 的自主性越强，对上下文和 Skill 的依赖就越弱
  2. Skill 是核心，上下文和 Agent 都是它的附属实现
  3. 上下文的稀缺性是对 Agent 的第一约束，而 Skill 是为化解这种约束而生的工程答案之一
  4. 只要上下文窗口足够大，Skill 就完全没有必要存在
答案与解析

答案：C。D 很具迷惑性：窗口再大也无法解决"知识跨会话持久""随仓库共享""成本随长度增长"三个问题，Skill 的价值不因窗口变大而消失。A 相反——自主性越强、循环越多轮，对上下文管理与 Skill 规范的依赖反而越强。（章节 03、04）

挑战10. 在"本次作业"这个闭环实例中，最后一个环节"沉淀"具体指的是？

  1. 把三份 HTML 学习资料上传到 GitHub
  2. 把"九部分结构 + 来源逐条核实 + 自检清单"这套被验证有效的流程写成 SKILL.md，供下一个概念直接复用
  3. 把对话记录保存成截图
  4. 把模型生成的答案背下来
答案与解析

答案：B。"沉淀"指把一次成功的做法从易失的对话历史搬进持久的文件资产——这正是 Agent → Skill 那条回环弧线的含义：教一次，永远会。（章节 05 的关系图与闭环说明）
